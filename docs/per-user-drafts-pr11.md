# PR #11 — 多人各自草稿與送審規則

此文件同時是 PR #11 的實作邊界與驗收規格。程式已接入現有製程編輯台、版本確認平台及 A／B／C／PROCESS／BOM 主資料後台；Staging、合併與正式 Site 發布仍依 `AGENTS.md` 與 `DEPLOYMENT.md` 關卡執行。

## 已確定的規則

1. 每個登入員工對同一製程工作區或同一後台資料項目，可獨立儲存與重開自己的草稿；儲存不修改他人的草稿、已生效內容或待審單。同一帳號多裝置與多分頁必須由伺服器辨別版本，舊畫面不能覆蓋新存檔；單帳號單一有效登入另須按已定政策檢查。
2. 儲存成功必須等伺服器確認；失敗仍保留目前畫面與可復原資料，不顯示成功。
3. 一次送審整份草稿。一筆資料已有別人的待審單時，整份送審暫緩，草稿保持可編輯；員工在草稿區塊下方看到「等待審核」、受影響資料與暫時差異。不得在尚未審完時要求員工接受尚未生效的值。
4. 第一張單核准或退回後，第二位員工按送審時重新讀取伺服器現況並比對草稿建立時的依據。退回且沒有其他衝突即可送審；核准後對有重疊修改的欄位顯示「原值／目前生效值／我的草稿值」。例如 B1／B2／B3，員工必須選擇採用 B2 或明確確認要以 B3 作為新提案。未解決任一衝突時整份暫緩。
5. 衝突畫面固定在草稿區塊下方，僅在待審或衝突時出現。每列有資料識別、欄位、三個值與「前往修改」按鈕，應定位到實際工段、流程與欄位；按鈕不可靜默改寫草稿。處理後重新檢查，不依賴舊畫面上的結果。
6. 送審成功才鎖定該份草稿，形成待審單。主管確認時再核對待審單依據與現行版本；不相符即停止，不寫回舊值。送審、確認及退回由伺服器權限與版本檢查執行，不靠前端按鈕禁用。
7. 甲與乙操作不同資料時可以各自儲存；同一草稿有多筆，任何未解決項目都暫緩整份送審，保留其他已編輯內容。


## PR #11 範圍與後續整合

- 本 PR 只實作目前 GitHub 原始碼中已存在的中控系統草稿／送審入口：製程編輯台、製程版本確認平台與現有主資料後台（A／B／C 線別、工段、產品及 BOM）。優先讓現場員工能用不同帳號各自儲存，解決同筆送審等待與審後差異。
- 共用的伺服器規則須按登入者與資料識別隔離草稿，儲存、送審及核准都核對版本並保留歷史；各頁面將「等待審核／衝突」面板放在自己的草稿區塊下方，按「前往修改」定位到實際資料。不同資料不能因共用全站修訂號而不必要地互相卡住。
- 品質系統 FQC、IQC、IPQC-AB、IPQC-C、檢具與測試設備，以及本機尚未完成或未推送的其他中控頁面，留待後續另一張 PR。後續 PR 要沿用本次完成的共用規則並逐頁接入、逐頁驗收；合併程式本身不會讓新頁面自動具備多人草稿。
- PR #11 的完成描述必須限定為已接入及實測的中控頁面。尚未接入的品質頁與本機頁面不得宣稱已完成或已測試；後續品質整合不可阻擋本次現場修復。

## 實作與驗收

- 先梳理製程編輯台與各後台資料庫的草稿鍵、權限、狀態和待審單；不得把共享的 `approvalVersions` 或 `processEditor:<category>:<line>` 當作每個人的獨立草稿。沿用現有 D1/R2 並保留歷史資料、媒體參照和權限。
- 以隔離 D1/R2 驗證甲乙同筆及不同筆儲存、等待待審、核准／退回後重比、B1／B2／B3 引導、整份暫緩、解衝突重送、主管競爭確認、登入與同帳號舊畫面、重新開啟草稿及失敗保留。
- 製程編輯台與現有主資料後台都需有對應驗收，不得以單一畫面成功宣稱中控頁面全部完成。桌面及 iPhone 尺寸檢查提示、差異表與「前往修改」的可用性。
- PR #11 保持 draft 直到實作、CI 與隔離 Staging 測試完成；不要改正式 Site。
